# Corpus Agent

## Purpose

Analyze multi-format technical document corpora, detect checklist findings, and support document-grounded chat.

## Maturity

**Status:** To be confirmed. Existing functional claims were not revalidated during the documentation reorganization.

## Features

- Upload and synchronize DOCX, XLSM, and PDF corpora.
- Parse, chunk, index, and deduplicate documents.
- Cross-check mapped spare-part and tooling references against project reference workbooks and BASL.
- Run editable checklist analysis through Mistral.
- Stream project analysis and grounded chat over SSE.

## Auth

**Tier:** 1 - local only, bound to `127.0.0.1`, with no authentication in the local-first profile.

## Port

The target default port is `8001`, followed by the next free port when needed. The current Unix and development defaults are known to differ and require a separate launcher correction.

## Prerequisites

Python 3.11+, Node 20, pnpm 9, and a Mistral API key for analysis and chat. Tesseract is optional for local OCR fallback.

## Start On Windows

Double-click `start.bat`.

## Start On Unix

Run `bash start.sh`.

## Frontend Development

From the repository root, run `pnpm dev:corpus-agent`.

## Served Interface

FastAPI serves the built React/Vite application from `frontend/dist/` at `/`.

## Persistence

SQLite stores projects, document metadata, chunks, findings, chat sessions, and runtime configuration under the gitignored `backend/data/` directory.

## LLM Configuration

Checklist analysis and chat are LLM-driven. When LLM use is disabled, the checklist is skipped and analysis still returns HTTP 200; mapped reference/BASL cross-checks remain available.

## Tests

Use the backend pytest suite and the frontend scripts declared in `frontend/package.json`. The synthetic cross-domain benchmark is in `backend/tests/fixtures/evaluation/benchmark-v1.json`; its deterministic scorer is tested without an API key. The repository also declares `test:e2e:corpus-agent`.

## Demo Mode

Demo mode exposes exactly one synthetic project in project selectors, dashboard KPIs, the knowledge view and the chat scope. Normal-mode projects remain stored and reappear when demo mode is disabled. Creating, renaming or deleting projects is unavailable in demo mode; document analysis and reference/BASL workflows remain available within the demo project.

Settings offers a Normal/Demo selector (`GET/POST /api/v1/settings`, `demo_enabled` stored in `AppConfig`, preserved by admin reset). In demo mode a badge appears in the sidebar and the Data tab is hidden (`/data` redirects to the dashboard). Enabling the mode creates a synthetic project with three multi-sheet maintenance XLSX files, plus BASL and reference workbooks with explicit mappings. Their cross-check illustrates a missing tooling reference (`TL-9999`); a fresh analysis reproduces the finding deterministically, even with the LLM disabled. Four seeded analysis runs show anomaly counts decreasing over time, and the synthetic findings span several categories, severities, confidence levels and statuses. Everything is generated by `backend/app/core/demo_seed.py`; leaving the mode removes the project, its anomalies and its stored files. Seeding is idempotent and reads no user data. See [demo mode guide](../../docs/standards/demo-mode-integration.md).

## Tickets and Knowledge

Knowledge includes a collapsed connectivity diagram of existing inputs, analysis, human review and correction memory. Each input has a keyboard/hover tooltip describing its actual analysis triggers and limitations; availability probes are detailed below. Chat is accessed using the floating bottom-right button, which opens a non-modal right-hand panel without navigating or discarding page edits. The panel fills small screens, supports Escape/close and focus return, and includes a collapsed history plus a new-conversation action. Conversation, project scope and unsent draft remain in memory across closing/reopening; no chat data is persisted in browser storage. Background streaming continues while closed, and conversation switching is disabled during streaming. Project scope is chosen explicitly, not inferred from the underlying page. The old `/chatbot` link opens the panel over the dashboard. Normal page navigation still honors the unsaved-changes guard. LLM settings start collapsed even when no key is configured.

Demo projects and their documents, reference sources and connected folders are excluded from normal-mode project access, including leftover demo records. Checklists are stored separately per mode (`rules.json` for normal use, `rules.demo.json` for demonstrations); editing, importing, validating or resetting one does not affect the other. Browser query caches, chat and project selections reset on mode changes. Leaving demo mode removes the generated project; its external OneDrive fixture files are not deleted or connected to normal projects. The demo folder path is remembered separately and restored only when recreating the demo project; restoring the path does not automatically ingest external files.

Generated demo projects remain identifiable after a rename through their exact generated description. Administration entity counts and project storage sizes follow the visible mode, while the SQLite size remains the physical shared database size. French Settings and Data labels translate conversation history, control lists, severity levels, analysis runs and indexed excerpts; machine severity values remain unchanged in API payloads.

Settings file selectors use `FileDropzone` from `@internal/ui` with explicit FR/EN labels, rather than native file-input captions that depend on the browser language. File-type restrictions, single-file selection and checklist inspection/reference extraction remain unchanged.

The Data tab is removed in both normal and demo modes. Existing `/data` URLs redirect to the dashboard. Administration APIs remain available; this navigation change does not delete data.

The diagram polls `GET /api/v1/health/connectivity` every five seconds while open and visible, with an immediate manual refresh and a server check timestamp. The endpoint checks current source existence, file/directory type and OS read permissions (plus traversal permission for folders) for the latest stored document versions and visible projects' folders/reference/BASL paths, without reading document contents. Missing, inaccessible or wrong-type sources turn red; absent sources remain grey; accessible ones turn green. This metadata probe does not validate document contents, folder synchronization freshness or mappings. Network filesystem calls may delay a check; the timestamp identifies the last completed probe.

AI enabled/disabled is displayed separately from provider availability. With AI enabled and a configured key, each probe makes a bounded (three-second HTTP timeout) authenticated `/v1/models` request, matching the Mistral client's base URL convention, without redirects or user documents, and displays connected/rejected/unreachable. No provider request is made when disabled or without a key. A failed probe invalidates the previous successful connection test so the standard `/health` badge no longer stays ON after its next refresh; a successful probe alone never validates generation/embedding models. Run the Settings connection test again to restore the tested state. Rule activation is polled alongside connectivity. Closing the diagram stops polling; this is not a continuous filesystem watcher. Result nodes remain illustrative, not activity indicators.

The dashboard displays aggregate indicators only, not the ticket list. Tickets remain in the editor view, which defaults to all projects and supports selecting one project. File groups start collapsed. Status changes refresh both tickets and dashboard KPIs.

Knowledge is grouped by checklist subject (ignoring case, accents and surrounding whitespace). Each theme lists distinct recommendations from tickets marked fixed, supporting correction counts, document/project coverage, the latest resolution date and collapsible source details. Open/acknowledged tickets on the same theme are shown as remaining work, not as proven recurrences of the same cause. This is traceable correction memory, not model retraining, automatic validation of file edits or automatic adoption of new analysis rules.

The knowledge overview quantifies retained corrections, distinct recommendations per theme, unique contributing documents and covered themes across all visible projects, independently of search. Corrections without recommendations are identified as still requiring formalization. A collapsible progression table reconstructs daily additions and cumulative totals from usable resolution dates (UTC) of currently fixed tickets; undated corrections remain counted in the overview but not in the timeline. Reopening or deleting a ticket changes this reconstruction: it is not an immutable event history, a reuse counter or evidence of productivity gains.

## Limitations

OCR quality depends on source documents and optional local tooling.
Changes made through the application (file uploads, corpus synchronization, reference/BASL updates and mapping changes) trigger a new analysis. External edits made directly in a connected folder are detected on the next folder synchronization; there is no continuous filesystem watcher.

## Standard Deviations

- Checklist rules remain editable and LLM-driven; mapped reference/BASL cross-checks are separate deterministic controls and remain available with the LLM disabled.
- App-specific page styling remains in the preview skin; the shared shell,
  navigation, theme/language controls, and LLM status use `@internal/ui`.
- Deployment-oriented hardening remains outside the local-first profile.
